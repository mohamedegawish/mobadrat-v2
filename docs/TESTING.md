# الاختبارات — كيف نتأكد إن المنصة شغالة

أربع طبقات، كل واحدة بتجاوب على سؤال مختلف:

| الطبقة | السؤال | المكان | الأمر |
|---|---|---|---|
| اختبارات الـ backend | هل كل قاعدة في المنصة والمبادرتين صح؟ | `backend/tests`, `backend/src/initiatives/*/tests` | `cd backend && npm test` |
| Hard tests (الصلابة) | هل المنصة بتصمد قدام مدخلات عدائية وتوكنات مزورة وطلبات متزامنة؟ | `backend/tests/hardening.test.ts` | `cd backend && npm test -- core hardening` |
| E2E (المتصفح) | هل رحلة المستخدم من الصفر شغالة من الشاشات زي ما هي؟ | `e2e/tests` | `cd e2e && npx playwright test` |
| Load test (الحمل) | كام مستخدم في نفس الوقت والمنصة مستحملة، وأنهي endpoint أبطأ؟ | `perf/` | `node perf/run.mjs prepare` ثم `node perf/run.mjs load` |

كلها محلية بالكامل: قواعد بيانات منفصلة لكل طبقة، والبريد إما متسجل في ملفات أو متقفل، ومفيش أي حاجة بتتبعت لسيرفر خارجي.

## المتطلبات

```bash
docker compose -f docker-compose.dev.yml up -d mysql                     # MySQL 8.4 على 3306 (e2e + load)
docker compose -f docker-compose.dev.yml --profile test up -d mysql-test # MySQL على 3308 (tmpfs) لاختبارات الـ backend
```

## 1. اختبارات الـ backend

```bash
cd backend
npm test                        # كل الملفات (المنصة + شمس الصناعة + صُنّاع المستقبل)
npm test -- core                # المنصة فقط        npm test -- sona3 09-reports   (ملف بعينه)
npm run typecheck && npm run lint:async
```

كل ملف اختبار بيعمل قاعدة بيانات مؤقتة خاصة بيه ويمسحها في الآخر.

## 2. Hard tests

`backend/tests/hardening.test.ts` (H-01 … H-10):

- **H-01:** توكنات مزورة: توقيع غلط، `alg: none`، HS512، refresh مكان access، منتهية، مستخدم ممسوح، نسخة قديمة.
- **H-02:** إلغاء الصلاحية فورًا: إيقاف الحساب، تغيير كلمة المرور، إيقاف العضوية.
- **H-03:** عزل المبادرات والأدوار عن بعض.
- **H-04:** mass assignment: حقول ممنوعة في التسجيل والملف والتسجيل في مبادرة وتعديل الأدمن.
- **H-05:** مدخلات عدائية:
  - body حجمه 2MB؛
  - JSON بايظ؛
  - `__proto__`؛
  - نصوص injection؛
  - أرقام صفحات خيالية؛
  - HTML داخل البريد.
- **H-06:** مستندات الملف الشخصي:
  - PDF مزيف أو امتداد غلط؛
  - ملف أكبر من الحد؛
  - اسم ملف خبيث؛
  - تحميل مستند شخص تاني.
- **H-07:** مفيش طريقة تعرف بيها إذا كان البريد مسجل ولا لأ.
- **H-08:** سباقات:
  - 8 تسجيلات بنفس البريد في نفس اللحظة؛
  - تسجيل صُنّاع المستقبل المتزامن؛
  - 5 طلبات تسجيل في مبادرة في نفس اللحظة؛
  - 5 حفظات متزامنة للملف.
- **H-09:** الهيدرز الأمنية و CORS والكوكيز.
- **H-10:** حدود الطلبات الحقيقية (RATE_LIMIT_SCALE=1).

## 3. E2E (Playwright)

```bash
cd e2e && npm install && npx playwright install chromium
npx playwright test                                   # الكل بالترتيب
npx playwright test --project platform --no-deps tests/account.spec.ts   # ملف واحد من غير ما يشغّل اللي قبله
JOURNEY_SHOTS=../shots npx playwright test --project sona3               # صور لكل مرحلة في الرحلة
```

بيشغّل الـ API بتاعه على :5200 بقاعدة `mobadrat_e2e` جديدة كل مرة، ومعاها الـ demo seed. الواجهة بتشتغل على :5273. أي بريد بيطلع بيتكتب كملف، عشان الرحلات تفتح روابط التفعيل والاستعادة الحقيقية. الترتيب كالآتي:

1. **`shams`:** الـ 14 spec بتوع التطبيق القديم، منقولين زي ما هم.
2. **`shams-mobile`.**
3. **`sona3`:** الرحلة الكاملة من التسجيل لحد COMPLETED، ومعاها الفروع.
4. **`platform`:** الرحلات اللي بتعدي على أكتر من مبادرة، ودليل الجهات، وحساب المنصة (`account.spec.ts`).

`account.spec.ts` بيغطي:
- **حساب جديد من الصفر:**
  - رفض الدخول قبل التفعيل مع زرار إعادة إرسال الرابط؛
  - التفعيل من البريد؛
  - رفض كلمة المرور الغلط؛
  - صفحة «مبادراتي» فاضية؛
  - «بياناتي» بتتحفظ وتفضل موجودة بعد إعادة التحميل.
- **نسيت كلمة المرور:**
  - الرابط بيشتغل مرة واحدة بس؛
  - كلمة المرور القديمة بتتقفل؛
  - البريد غير المسجل بياخد نفس الرد.
- **حساب منصة بيقدّم على شمس الصناعة:**
  - بيانات المنشأة بتتدخل مرة واحدة، والمستندات بتتنقل لوحدها؛
  - المعالج بيفتح ومتعبي؛
  - الفواتير والإرسال؛
  - المبادرة مقفولة طول ما الطلب في مراجعة IMC؛
  - بتتفتح بعد القبول.
- **الإدارة بتوقف عضوية وبتوقف حساب:** الجلسة المفتوحة بتتأثر فورًا، وبعدين بيرجعوا الاتنين.
- **الإشعارات الموحدة:** قرار في المبادرة بيوصل للجرس وصفحة الإشعارات، وفتح الإشعار بيفتح الشاشة بتاعته.
- **الموبايل:** كل الصفحات على مقاس شاشة Pixel 7 من غير scroll أفقي.

## 4. Load test (k6)

```bash
node perf/run.mjs prepare        # قاعدة mobadrat_perf جديدة + بيانات تجريبية كبيرة عن طريق الـ API نفسه (~12 دقيقة)
node perf/run.mjs load           # build إنتاج + endpoints + mixed (50/150/300/500 مستخدم) + stress → perf/.state/results/report.md
node perf/run.mjs load mixed     # جزء واحد بس      MIXED_LEVELS=100,200 MIXED_DURATION=2m node perf/run.mjs load mixed
```

- **البيانات (`perf/seed.mjs`):**
  - 1000 مصنع في شمس الصناعة، متوزعين على كل مراحل المسار والنهايات (رفض، انسحاب، تعاقد).
  - 1000 متقدم في صُنّاع المستقبل، من المسودة لحد التقييم.
  - 500 حساب منصة من غير مبادرة.
  - كله بيتعمل بتسجيل حقيقي، وتفعيل من البريد، وقرارات حقيقية من الموظفين. مفيش إدخال مباشر في الجداول.
- **السيرفر:**
  - `NODE_ENV=production` من الـ build نفسه.
  - حدود الطلبات حقيقية.
  - `TRUST_PROXY=1`: كل مستخدم افتراضي ليه عنوان IP خاص بيه.
  - مفيش ناقل بريد خالص، فمفيش ولا رسالة ممكن تخرج من الجهاز.
- **السيناريوهات (`perf/k6`):**
  - **`endpoints.js`:** كل endpoint لوحده تحت ضغط متواصل، عشان نرتبهم من الأبطأ للأسرع.
  - **`mixed.js`:** خليط واقعي من الزوار والمصانع والمتقدمين والموظفين والإدارة، مع وقت قراءة بين كل شاشة والتانية. بيشتغل على مستويات متدرجة من عدد المستخدمين.
  - **`stress.js`:** معدل طلبات بيزيد لحد ما المنصة تتشبع.
- **الأمان:** الأدوات بترفض أي هدف غير `127.0.0.1` أو `localhost`. ممنوع تشغيلها على سيرفر مشترك أو على الإنتاج.
